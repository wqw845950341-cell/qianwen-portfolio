# 巷遇 LaneMuse｜AI CityWalk 城市文化探索助手

产品需求文档 v1.0 · 2026-11-10 · 作品集概念项目

文档状态：功能基线已定义，视觉方向已选择并完成前端交互原型（见第16节）。目标载体为手机端 H5 / 微信小程序。本文中的画像、痛点、优先级和目标值为产品假设；没有开展真实访谈、上线实验或取得商业成果。界面中的路线为演示数据，不作为真实出行依据。

## 1. 项目背景与产品定位

自由行游客需要在攻略、地图和文化资料之间切换，才能把“想去的地方”组合成时间、体力和预算都可承受的一段步行体验。巷遇提供从行前规划到行中文化探索的连续服务：输入目的地、时长、兴趣、预算和步行强度，获得可解释的路线，边走边了解地方文化，并按当前情况调整余下行程。

一句话价值：让每一次城市漫步，都有适合自己的路线和听得懂的故事。

首期范围：上海一个经人工核验的文化街区，约 30 个 POI、8 条种子路线、中文体验；产品采用适合国际旅游产品的信息层级、图标和排版，但首期不宣称全球覆盖或多语言服务。后续按数据覆盖逐城扩展。

产品目标：减少用户规划负担，提高路线实际可执行性，让用户在到访中完成至少一次有来源的文化探索。

商业假设：先验证路线与文化讲解价值，再探索付费主题路线、文化机构合作和城市内容服务。MVP 不提供票务交易、广告竞价排序或导游撮合。

## 2. 用户画像与任务

| 假设画像 | 场景与限制 | 核心任务 | 成功表现 |
| --- | --- | --- | --- |
| 自由行游客，首次到访 | 酒店入住后有 2–4 小时，陌生路网、时间有限 | 在可用时段内体验代表性街区 | 不绕路、不赶路，知道为何值得去 |
| 本地城市探索者 | 周末半天，熟悉热门景点，希望寻找新角度 | 按建筑、历史、生活方式探索熟悉的城市 | 发现新故事，并能沿途追问 |
| 轻体力文化爱好者 | 1–3 小时，重视休息与步行量 | 获得短距离、有休息点的文化路线 | 总距离可控、能跳过一站 |

优先服务前两类；“轻松”是距离与节奏选项，不等同于已验证的无障碍路线。

JTBD：当我只有一段有限的空闲时间，又不熟悉当地时，我希望获得一条符合兴趣、能实际走完且能理解文化背景的路线，从而减少临场决策，把精力留给体验。

## 3. 痛点、需求与验证计划

| 痛点假设 | 对应需求 | 产品回应 | 待验证方式 |
| --- | --- | --- | --- |
| 收藏很多地方却不会串联 | 可执行的时空安排 | 时间窗、步行路网、停留时长共同校验 | 访谈 8–12 人，观察真实规划过程 |
| 热门路线不适合个人兴趣与体力 | 个性化约束 | 五项参数与推荐理由 | 任务测试对比统一路线与个性路线 |
| 到场后只看外观，资料过长 | 简短、有来源的文化解释 | 30 秒导读、2 分钟讲解、上下文问答 | 现场测试理解度与内容反馈 |
| 下雨、疲劳、闭馆导致计划失效 | 局部调整与确认 | 跳过/替换、缩短路线、调整前后对比 | 模拟闭馆和疲劳任务 |
| AI 内容可能不准确 | 可追溯、可纠错 | 事实来源、更新时间、无依据时拒答 | 内容专家抽检、对抗题集 |

研究输出应包括去标识的访谈记录、问题频率、原话证据和反例。本项目当前不填造访谈语录、市场规模或竞品表现数据。

拟做替代方案比较：地图工具的路网与导航能力、图文攻略的灵感与内容、通用 AI 的自然语言理解。这里只定义比较维度，不在未实测时断言其缺陷或转化表现。

## 5. 用户流程与信息架构

主流程：进入首页 → 搜索目的地或选择编辑路线 → 设置偏好 → 校验输入 → AI 生成及路网校验 → 查看路线结果 → 点击站点 → 阅读/播放讲解 → 开始漫步 → 导航至下一站 → 手动确认到达 → 继续探索 → 结束与反馈。

调整流程：路线结果或行中打开 AI → “走少一点”或自由输入 → 提取变更 → 保留已完成点，重新规划未完成点 → 展示新增/删除站点与时间、距离、花费变化 → 应用新版本 / 保留原路线。

异常分支：定位拒绝 → 手动选起点；生成超时 → 保留输入并重试/改看种子路线；约束冲突 → 明示冲突并请用户放宽；景点关闭 → 提示替换，不静默删除；文化证据不足 → 展示已有资料并说明无法确认；导航拉起失败 → 显示地址、复制地址和路线列表。

信息架构：

- 发现（首页）：城市选择、搜索、编辑精选、进入行程设置。
- 我的路线：本机保存路线、最近进行中的路线、删除和数据清除入口。
- 行程设置：基础条件、兴趣和节奏、生成进度。
- 路线工作区：地图/列表、路线摘要、站点、保存、开始、调整。
- 景点详情：实用信息、文化讲解、来源与反馈。
- AI 抽屉：挂载路线/景点上下文；不另设独立社交聊天首页。

返回规则：详情返回保持地图中心、抽屉展开度与选中站点；设置返回保留草稿；退出行中先询问是否结束，切后台不自动结束。

## 6. 输入与规则（F01–F03）

目的地必填，仅开放已覆盖城市/街区，搜索为空明确提示覆盖范围。城市不能被定位权限隐式覆盖。起点可由搜索、地图选点或本次授权定位获得；默认建议“路线起点”，用户可改。

时长：1/2/3/4/6 小时，默认 3 小时。日期默认客户端当地今日，时间默认当前时间向后取最近 15 分钟刻度并允许修改；跨日方案不支持。兴趣必选 1–3 项：历史、建筑、在地生活、美食、艺术，默认建筑+历史。预算为每人全程上限，人民币，0–1000 元，默认 120；包括门票和计划内餐饮，不含到达起点与离开终点的交通；同时呈现估算区间和未知项目。

强度：轻松（总步行 ≤2km，估算速度 3km/h）、适中（≤4km，4km/h）、深入（≤7km，4.5km/h）；不是健康能力判断。步行用时取“地图返回时长”与“路程/选定速度”较大值，并另加过街/休息缓冲。

总时长 = 步行 + 各站停留 + 休息及过街缓冲；不超过用户时长。闭馆、不可步行、必需预约但未确认、预算估算上界超出上限的方案不得直接标为“符合偏好”。营业或价格未知时显示待确认，并优先使用可靠替代点；若没有可行路线，返回明确原因和用户可选择的放宽条件。

生成结果默认一条推荐路线；修改偏好可重新生成，不堆叠三个无法校验的 AI 方案。推荐解释最多三条，指出兴趣、时间或节奏匹配依据。返回起终点、各段步行、停留、预约提示、费用构成、数据更新时间和风险提示。路线命名由 AI 生成，但站点 ID 必须来自候选库。

## 7. 页面与交互需求

### S01 首页（F01/F09）

首屏含品牌、城市、目的地搜索、主按钮“规划我的漫步”、一条编辑精选及“我的路线”入口。精选注明主题、时长、距离，点击进入路线结果并可修改偏好。不出现未定义的积分、排行榜、社交或订票入口。首次访问不弹登录与定位请求；用户点定位时解释用途。

### S02 AI 行程设置（F02/F03）

分为“去哪里/什么时候”和“怎样探索”两组，底部固定生成按钮。已选值直接可见，预算和强度配简短说明。字段校验在原位呈现；提交后避免重复请求，草稿保留。进度显示“理解偏好→匹配地点→校验步行路线”，仅在实际完成阶段后切换，不展示伪造百分比。

### S03 路线结果与行中状态（F03/F04/F07/F08/F09）

地图占主要区域，摘要按“路线主题→总时长/总距离/预计费用→站点顺序→单站文化亮点”排列。摘要旁明确“游览约 3 小时”而非让用户误解为纯步行时间。地图点位编号与列表一致；路径箭头表达行进方向；起点/终点文字标识，不能仅靠颜色区分。

底部抽屉三挡：收起约 24%（摘要与主操作）、半屏约 52%（前两站和段间距离）、展开约 88%（完整时间线）。拖拽柄、点击展开按钮都可操作；列表滚动与地图拖动分区。点击地图点 → 高亮并定位对应列表行；点列表行 → 选中点位且避免被抽屉遮挡；二次点“查看景点”进入详情。默认缩放展示全路线，手动拖动后不强制回中心；“全览”“定位”可重置。

底部主要操作“开始漫步”，次要操作保存；AI 入口为“问问巷遇”，打开抽屉。开始后摘要替换为“下一站/剩余时间”，主按钮为“去下一站”。地图与详情中的导航均导航到选定站点。到达由用户手动确认；不把导航拉起等同于真实到达。

完成点、当前点、待访问点以图标+文字表达；跳过站点不会计为到访；只更新未完成路段。返回外部地图后保留本地路线状态，导航结果未知时仍等待用户确认。

### S04 景点详情（F05/F06/F08/F10）

内容顺序：地点名与图片→为何值得看→营业/地址/价格/预计停留/预约→30 秒导读→2 分钟文化讲解→来源与更新时间。首期提供中文；英文名称是品牌辅助排版，不表示可切换语言。

文化内容分“可核实事实”“观察提示”“有出处的地方传说”，不把传说写成定论。文本先提供摘要，长内容可展开。播放由用户点击触发，可暂停/继续/进度拖动，离开详情暂停；TTS 不可用保留全文。每篇讲解绑定来源，用户可打开来源说明与原始链接；问题内容可反馈。主操作“导航到这里”，辅助“问问这栋建筑”。

### S05 AI 对话与调整（F06/F07）

从路线进入时上下文条展示“基于当前 5 站路线”；从景点进入展示“正在聊：武康大楼”。文字输入、发送、流式输出、停止生成、重试；不提供未定义的录音按钮。预设追问“为什么推荐这里”“走少一点”“这栋建筑有什么故事”。键盘弹出后输入区保持可见。

介绍型问题直接回答并附内容来源；路线修改型问题先生成变更预览，显示旧→新站点数、总距离、总时长、费用和原因，再由用户点击“应用调整”。取消不改变原路线。多条请求排队或取消前一条，版本冲突时要求重新预览。用户可退出对话，保留本次会话。

## 8. AI Agent 工作流与系统边界

采用单编排器调工具与确定性校验器，不把多个聊天角色堆成不必要的多 Agent 系统。

1. 理解输入：结构化 city、start、date_time、duration_min、interests、budget_cap、walking_level、locale。用户文本与工具内容作为数据处理，不允许改写系统规则。
2. 完整性检查：关键字段缺失时只问一个最必要的问题；表单默认值已展示并被提交则不再追问。
3. 候选召回：POI 库按地理边界、兴趣、营业、价格与审核状态筛选；召回约 15–25 个候选。
4. 步行算路：地图工具返回候选间实际步行距离、时长与路径；缓存遵守供应商约定。直线距离只能用于初筛，不能作为最终路线距离。
5. 路线求解：在时间窗、距离、预算和可达性硬约束下选点排序；可用启发式搜索，不宣称全局最优。排序偏好可先设兴趣 40%、文化质量 30%、减少折返 20%、多样性 10%，后续由测试调整。
6. 内容检索：只从通过审核的文化知识条目检索，返回 source_id、claim_id、版本、适用 POI 和更新时间。
7. 生成：模型组织推荐理由和讲解，不修改工具计算的距离、价格、开放时间。结构化输出经 schema 校验；不输出内部推理过程。
8. 硬校验：点位 ID 存在；各段可达；到达与停留处于开放窗；总时间、费用上界、强度符合输入；文化事实可回溯。失败至多两轮修复，再返回可解释失败及种子路线入口。
9. 发布：生成 route_id、version、数据时间和可读解释。应用调整写入新版本，旧版本留作撤销依据。
10. 行中触发：用户主动报告疲劳/下雨/关闭或变更时间 → 固定完成站点 → 重新执行剩余路线校验 → 用户确认后生效。MVP 不承诺后台实时监控天气或营业状态。

工具契约：search_poi 返回 POI ID、坐标系、核验状态；walk_route 返回 polyline、distance_m、duration_s；get_opening_hours 返回时间窗与时效；retrieve_culture 返回带来源片段；validate_route 返回通过/失败原因。超时、配额、空结果与版本均为显式状态。

AI 拒答原则：没有证据时说明“现有资料无法确认”，可以提出可观察的建筑细节，不编造年代、人物轶事、门票和开放信息。用户请求进入封闭区域时只推荐公开可达路线。

## 9. 数据模型、来源与运营

| 实体 | 核心字段 |
| --- | --- |
| TripPreferences | city_id、start_poi/coordinate、出发时间及 timezone、duration_min、interest_tags、budget_cap、intensity |
| POI | id、名称、地址、坐标与坐标系、类别、时间窗、费用区间、预约、建议停留、来源、verified_at、状态 |
| CultureEntry | poi_id、fact/observation/legend、内容、claim_source_map、source_url、版权、审核人、语言、版本 |
| Route | id、version、preferences_snapshot、ordered_stops、legs、分项时间/花费、估算区间、validated_at、状态 |
| VisitSession | route_id/version、current_stop、手动到达时间、跳过记录、开始/结束状态 |
| Conversation | context_type、route_version、poi_id、messages、引用来源、待应用变更 |
| Feedback | target_id、版本、问题类型、可选说明、处理状态 |

候选数据来源：地图供应商 POI/步行路网；场馆官方网站的营业、预约和价格；地方文旅机构、博物馆、地方志等可核验文化资料；人工采编图片或获授权图片；后续天气供应商。不能把公开网页等同于允许商用抓取和再分发。

高德官方文档提供步行规划服务；首期将它作为国内算路候选，实际配额、商用授权、地区覆盖及小程序接入在工程阶段确认。[官方路径规划文档](https://developer.amap.com/api/webservice/guide/api/direction)

外部地图导航存在客户端和容器适配条件，H5/微信环境必须分别验证拉起与回退路径。[官方导航 URI 文档](https://lbs.amap.com/api/uri-api/guide/travel/route)

文化素材须逐条记录授权与署名条件；即使同一机构，不同作品的许可也可能不同。[UNESCO 开放许可说明](https://www.unesco.org/en/open-access/creative-commons)仅作为许可审查参考，不代表所有城市文化素材均可复用。

更新策略（项目拟定）：出发前重新查验可用动态数据；营业与价格每日任务检测，计划使用 24 小时内核验记录；超过时效或供应商不支持更新时显示“待确认”。历史文化内容按季度复审或收到纠错即复审。图片与文化条目先审后发；严重事实错误和失效路线可立即下架。天气或实时人流未接入时不展示相关确定性标签。

运营闭环：选街区→核验 POI→建立来源条目→编辑种子路线→实地试走→审核发布→查看反馈→纠错与版本回滚。MVP 后台只需服务该闭环，不扩展营销 CRM。

## 10. 非功能要求与异常体验

- 性能验收目标：首个进度反馈 ≤1 秒；标准五站路线生成 P95 ≤20 秒，30 秒终止并提供重试；文化首段响应 P95 ≤5 秒。均为目标，需在指定网络、设备和供应商环境实测。
- 地图故障：保留可读站点列表和地址，不用示意地图冒充可导航路网。弱网保留已加载文本，不宣称离线导航。
- 可访问性：正文优先 16px、最小辅助文字 12px；可操作区至少 44×44 CSS px；目标普通文字对比度 ≥4.5:1；用颜色以外线索区分路线状态；地图提供等价列表；支持系统字号和减少动效。
- 隐私：仅用户点击定位时请求前台位置；不持续采集轨迹；分析事件不包含完整对话或精确位置。路线和会话本机保存可清除；拟定服务端会话最长 7 天、去标识质量日志 30 天，具体上线政策经用户授权方案确认。
- 安全：服务端保存密钥、输入限流、工具白名单；网页资料作为不可信内容，不能触发工具越权或读取密钥。
- 国际化预留：文案键、单位/币种/时区、文字扩展空间；首期只呈现支持的能力，不提供空语言切换器。

## 11. 核心指标与埋点

北极星：每周有效文化漫步完成次数。定义为同一匿名会话开始路线、手动到达至少 3 站（少于 3 站则全部）、完成至少一次有效文化阅读或播放并主动结束。它是产品内行为代理值，不能据此断言用户真实到访。

有效文化阅读：展开内容后前台停留累计 ≥30 秒；播放累计 ≥30 秒且未静音无法验证时只称播放，不称“听懂”。合并重复事件，以 session_id+route_id+version 去重。

| 指标 | 口径 | 首轮目标假设 |
| --- | --- | --- |
| 设置完成率 | 提交成功会话 / 打开设置会话 | ≥65% |
| 有效生成率 | 校验通过且结果渲染成功请求 / 有效生成请求 | ≥95% |
| 路线采用率 | 结果展示后本次会话点击开始 / 有效结果会话 | ≥35% |
| 文化内容触达率 | 打开文化内容的开始会话 / 开始会话 | ≥50% |
| 行程完成率 | 满足北极星条件会话 / 开始会话 | ≥40% |
| 调整采用率 | 应用变更 / 变更预览成功会话 | ≥50% |
| 内容来源覆盖 | 有来源事实条目 / 发布事实条目 | 100% |
| 路线硬约束通过率 | 抽检完全满足约束路线 / 抽检路线 | ≥95%；高风险可达错误为上线阻断 |

目标不等于成果。30 人测试或早期内测只能提供方向性信号，不展示没有统计依据的提升百分比。

埋点：home_view、destination_selected、preferences_open/submit/error、generation_start/success/fail、route_view/save/start、map_pin_select、stop_detail_view、culture_expand/play、source_open、chat_send/success/fail、replan_preview/apply/cancel、navigation_launch/fallback、stop_arrived/skipped、walk_end、feedback_submit。共用 event_id、匿名 session_id、页面、时间、route_version、实验组、错误码；不含精确位置和原始问答。

护栏指标：规划超时率、数据过期率、文化错误报告率、导航失败率、每条有效路线调用成本、误导性路线严重事件数。成本按模型 token、地图次数、TTS 字数和人工内容维护分别记录；先测出实际成本再定付费价。

## 12. 验收清单与可用性测试

| 场景 | 通过条件 |
| --- | --- |
| 正常规划 | 上海、3h、建筑+历史、120 元、适中，生成满足约束的路线并展示费用范围 |
| 参数冲突 | 1h 与远距起点冲突时说明问题，不静默扩成 3h |
| 地图联动 | 点第 3 站时列表与地图编号一致，详情返回位置不丢 |
| 文化提问 | 有依据则附来源；无依据不捏造；TTS 失败仍能阅读 |
| 调整路线 | 已完成站点不变，预览清楚，取消保持原版本，应用后摘要一致 |
| 权限/弱网 | 定位拒绝可手选；地图或 AI 失败均有下一步且输入不丢 |
| 外部导航 | 能按容器能力拉起；失败时有地址与复制入口，不冒充导航成功 |
| 数据一致 | 各段距离之和、时间分项、费用上下界与页面摘要一致 |

可用性计划：首轮 5 人形成性测试，游客/本地探索者均覆盖，观察能否无提示完成“设置→理解路线→查文化→缩短路线”；记录任务成功、犹豫点、错误和完成时间。第二轮再招 5–8 人复测。样本小仅报告人数与问题，不外推总体。

AI 离线评估：拟建 100 题集，常规约束 35、冲突约束 20、文化事实 20、无答案 10、工具失败与提示注入 15；比较无检索、检索增强、检索+规则校验三种配置。记录事实支持率、无答案正确拒答、硬约束通过率、延迟和成本，保留真实结果表空栏，测试后填写。

## 13. 原型范围与需求追踪

选定方向后的手机高保真原型至少包含：S01 首页、S02 行程设置、S03 路线结果、S04 景点详情及文化讲解、S05 AI 对话、S06 调整预览、S07 行中与结束反馈、S08 本机保存路线。S05/S06 主要以抽屉实现。

原型真实度约定：前端状态与流程可交互；AI 回复、路网与 POI 可用固定数据模拟并显著标注“演示”。没有接入真实地图时只呈现示意路线，不宣称真实导航；外部导航需要真实坐标和容器验证后才能启用。每个新增可见按钮必须映射 F 编号；未定义能力先补 PRD 再入原型。

统一演示数据集（所有方向共用）：“梧桐下的建筑漫步”，上海；3 小时、3.2km、5 站；预计每人 80–110 元，上限 120 元；建筑+历史、适中；顺序为武康大楼→武康路街区→巴金故居→安福路街区→乌鲁木齐中路。站点真实名称仅作概念场景，所有段距离、营业、票价和路线时序均为演示估算，待接 API 和实地核验。

时间账本：步行 48min（3.2km/4kmh）+ 停留 105min（20/20/25/20/20）+ 缓冲 27min = 180min。段距暂设 0.7/0.6/1.1/0.8km，合计 3.2km。演示费用 80–110 元作为餐饮预留，不写成未核实的场馆票价。方向图可仅显示摘要和前两站，完整时间线在原型中展开。
